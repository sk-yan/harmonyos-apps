# 应用版本与 Release

仓库收录多个应用，每个应用独立编号。一个应用发版，不需要提高其他应用的版本。

## 标签与版本

Git 标签格式为：

```text
<app-id>-v<version>
yibi-ledger-v1.0.0-preview.1
yibi-ledger-v1.0.0-preview.2
yibi-ledger-v1.0.0
```

首次一笔记账使用 `yibi-ledger-v1.0.0-preview.1`，并在 GitHub Release 勾选 **pre-release**。原生 `AppScope/app.json5` 的 `versionName` 是 `1.0.0`；Git 标签的 `preview.1` 说明这次分发的成熟度，不会自动改变原生包版本。更新原生包时需按 HarmonyOS 规则维护 `versionCode`，不要只改 Git 标签。

合集不使用一个全局版本代表所有 App。GitHub 的“Latest”可能只对应最近发布的某个应用；查找指定 App 时，应从根 README 或 `apps.json` 的具体标签进入。

## 一次发布包含什么

- **发布说明**：写清功能变化、源码提交、构建方式、验证设备和未完成项，使用[模板](../templates/release-notes.md)。
- **HAP**：只有实际成功构建的产物才能上传，文件名标注应用、版本和 `unsigned` 或 `signed`。签名包需说明签名类型及设备限制。
- **校验文件**：为上传附件生成 SHA-256，并在本地重新验证。校验值证明附件完整性，不证明应用已签名或运行正确。
- **应用源码包（可选）**：如提供，使用与标签提交一致的干净文件，排除本地数据、工具、缓存和签名资料。GitHub 自动生成的 Source code 包包含整个合集。

截图保存在应用的 `docs/screenshots/`，发布说明可引用对应标签下的图片。只使用测试账单等非个人数据。

## 发布检查

1. 确定要发布的应用和提交，检查应用 README、`apps.json`、原生版本和 Release 标签一致。
2. 运行本次修改涉及的检查。前端 CI 成功只覆盖工作流列出的步骤；原生编译、模拟器、真机和签名结果分别记录。
3. 对该提交构建新 HAP，确认不是旧副本中的历史产物。核验包名与版本，并检查附件不含签名秘密或个人数据。
4. 根据实际验证范围填写发布说明。构建失败、未签名、工具异常或真机未测要明确记载，不能靠“测试通过”一语带过。
5. 创建对应应用的标签与 Release，上传附件和校验文件。处于开发预览的版本始终标为 pre-release。
6. 重新打开 Release，核对标签、附件名称和校验值，确认目录链接指向这一版本。

前端 CI 本身不会签名、生成真机分发许可或发布到华为应用市场。GitHub Release 是源码和构建附件的分发入口；可安装设备范围取决于具体包的签名和系统要求。

## 本次一笔记账的边界

`1.0.0-preview.1` 是未签名的模拟器预览。已有 HarmonyOS 6.1.0（API 23）模拟器验收，使用 Mate X5 折叠屏模板；Mate X6 真机签名、安装和验收尚未完成。没有应用市场上架记录。

仓库尚未选定源代码许可证。不要在 Release 或宣传文案中将它标为 MIT、Apache 或其他开源许可。
